================================================================================
  DrillMonitorWeb — Инструкция по развёртыванию на Ubuntu Server
================================================================================

Версия: 1.0
Автор: Andrey Podlesnyy
Дата: 2026-04-26


1. ТРЕБОВАНИЯ К СЕРВЕРУ
────────────────────────────────────────────────────────────────────────────────
  ОС        : Ubuntu 20.04 LTS / 22.04 LTS / 24.04 LTS (64-bit)
  RAM       : минимум 512 МБ (рекомендуется 1 ГБ+)
  Диск      : минимум 500 МБ свободного места
  Сеть      : доступ к интернету (для установки пакетов)
              доступ к видеорегистратору по RTSP (порт 554)

  Необходимое ПО:
    • Node.js  v18 или v20 (LTS)
    • npm      v9+
    • FFmpeg   (для трансляции видео с регистраторов)
    • git      (для клонирования репозитория)


2. БЫСТРОЕ РАЗВЁРТЫВАНИЕ (через скрипт)
────────────────────────────────────────────────────────────────────────────────
  Запустите установочный скрипт от имени root или через sudo:

    sudo bash install.sh

  Скрипт выполнит все шаги автоматически: установит зависимости,
  настроит systemd-сервис и запустит приложение.


3. РУЧНОЕ РАЗВЁРТЫВАНИЕ (шаг за шагом)
────────────────────────────────────────────────────────────────────────────────

  3.1. Обновление системы
  ─────────────────────────
    sudo apt update && sudo apt upgrade -y


  3.2. Установка Node.js v20 (через NodeSource)
  ─────────────────────────────────────────────
    curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
    sudo apt install -y nodejs


  3.3. Установка FFmpeg
  ──────────────────────
    sudo apt install -y ffmpeg

    Проверка:
      ffmpeg -version


  3.4. Установка git
  ───────────────────
    sudo apt install -y git


  3.5. Клонирование репозитория
  ──────────────────────────────
    sudo mkdir -p /opt/drillmonitor
    sudo chown $USER:$USER /opt/drillmonitor
    git clone <URL_РЕПОЗИТОРИЯ> /opt/drillmonitor
    cd /opt/drillmonitor


  3.6. Установка зависимостей Node.js
  ─────────────────────────────────────
    npm install --omit=dev


  3.7. Создание системного пользователя (рекомендуется)
  ──────────────────────────────────────────────────────
    sudo useradd --system --no-create-home --shell /usr/sbin/nologin drillmonitor
    # Код — root, служба пишет только в server/data (см. раздел 17)
    sudo chown -R root:root /opt/drillmonitor
    sudo chown -R drillmonitor:drillmonitor /opt/drillmonitor/server/data

    Root-помощники и sudoers вручную ставить не нужно — их ставит install.sh
    (раздел 17). Без них не будут работать смена сети, часы и обновление.


  3.8. Настройка переменных окружения (опционально)
  ──────────────────────────────────────────────────
    По умолчанию сервер запускается на порту 3000.
    Чтобы изменить порт, передайте переменную окружения PORT:

      PORT=8080 npm start

    Или укажите в systemd-юните (см. ниже).


  3.9. Создание systemd-сервиса
  ──────────────────────────────
    Создайте файл /etc/systemd/system/drillmonitor.service:

    ┌──────────────────────────────────────────────────────────────────────────┐
    │ [Unit]                                                                   │
    │ Description=DrillMonitorWeb                                              │
    │ After=network.target                                                     │
    │                                                                          │
    │ [Service]                                                                │
    │ Type=simple                                                              │
    │ User=drillmonitor                                                        │
    │ WorkingDirectory=/opt/drillmonitor                                       │
    │ ExecStart=/usr/bin/node app.js                                           │
    │ Restart=on-failure                                                       │
    │ RestartSec=5                                                             │
    │ Environment=PORT=3000                                                    │
    │ Environment=NODE_ENV=production                                          │
    │                                                                          │
    │ [Install]                                                                │
    │ WantedBy=multi-user.target                                               │
    └──────────────────────────────────────────────────────────────────────────┘

    Активация сервиса:
      sudo systemctl daemon-reload
      sudo systemctl enable drillmonitor
      sudo systemctl start drillmonitor

    Проверка статуса:
      sudo systemctl status drillmonitor

6. НАСТРОЙКА ВИДЕО С РЕГИСТРАТОРА DAHUA NVR4104
────────────────────────────────────────────────────────────────────────────────
  Сервер транслирует видео по схеме:
    Регистратор (RTSP) → FFmpeg (HLS-конвертация) → Браузер (HLS.js)

  RTSP-адрес формируется автоматически из параметров виджета:
    rtsp://USER:PASS@HOST:PORT/cam/realmonitor?channel=N&subtype=0

  Требования к сети:
    • Сервер DrillMonitorWeb должен иметь сетевой доступ к регистратору
      на порту 554 (RTSP)
    • Браузеры клиентов обращаются только к серверу DrillMonitorWeb

  HLS-сегменты хранятся во временной директории:
    /tmp/drillmonitor_hls/

  Сегменты автоматически удаляются при остановке потока или сервиса.

9. ОБНОВЛЕНИЕ ПРИЛОЖЕНИЯ
────────────────────────────────────────────────────────────────────────────────
  Штатный путь — из BCS_DrillerMonitorLoader: «Обновление» на панели редактора.
  В интернет табло не ходит (ни шлюза, ни DNS), поэтому пакет привозит Loader —
  по RS-485 кадрами {"upd":…} или по TCP/IP запросом POST /api/update/package.
  Монитор сверяет контрольную сумму и передаёт пакет root-помощнику
  /usr/local/lib/drillmonitor/apply-update.py (раздел 17). Тот проверяет пути
  и ссылки, кладёт прежнюю версию в /opt/drillmonitor/backup/before-<дата>.tgz
  (хранит две последние), распаковывает архив поверх установки — при сбое
  возвращает прежнюю версию — и монитор перезагружается. server/data с базой
  профилей не трогается.

  Пакет обновления меняет только программу. Root-помощники (scripts/*.sh,
  scripts/apply-update.py) он не заменяет: новые их версии ставит только
  повторный запуск install.sh на месте.

  Зависимости без интернета поставить нечем: пакет без node_modules, у которого
  в package.json другие зависимости, монитор отклоняет — нужен полный пакет.

  Откат:
    cd /opt/drillmonitor
    sudo systemctl stop drillmonitor
    sudo tar -xzf backup/before-<дата>.tgz --no-same-owner
    sudo systemctl start drillmonitor

  Вручную, если Loader недоступен:
    cd /opt/drillmonitor
    sudo systemctl stop drillmonitor
    sudo git pull
    sudo npm install --omit=dev
    sudo bash install.sh          # права и root-помощники — к новой версии
    sudo systemctl start drillmonitor

11. УСТРАНЕНИЕ НЕПОЛАДОК
────────────────────────────────────────────────────────────────────────────────
  Первым делом — сводка самодиагностики (раздел 15):
    curl http://localhost/api/health | python3 -m json.tool

  Проблема: Сервис не запускается
    → Проверить логи: sudo journalctl -u drillmonitor -n 50
    → Убедиться, что порт не занят: ss -tlnp | grep 3000

  Проблема: Видео с камеры не отображается
    → Убедиться, что ffmpeg установлен: ffmpeg -version
    → Проверить доступность регистратора: ping <IP-регистратора>
    → Проверить RTSP вручную: ffplay rtsp://user:pass@host:554/cam/realmonitor?channel=1&subtype=0
    → Убедиться, что /tmp доступен для записи

  Проблема: Страница недоступна из сети
    → Проверить брандмауэр: sudo ufw status
    → Проверить, что сервер слушает все интерфейсы, а не только localhost

  Проблема: Ошибка "EACCES permission denied" на порту 80/443
    → Используйте порт выше 1024 (по умолчанию 3000) или настройте Nginx как
      обратный прокси


12. ВРЕМЯ СЕРВЕРА (СИНХРОНИЗАЦИЯ С BCS_LOADER)
────────────────────────────────────────────────────────────────────────────────
  В сети буровой нет интернета и NTP, а RTC сервера может не держать время.
  Источник времени — BCS_DrillerMonitorLoader: поле `time` (время сбора
  данных, UTC) каждого push-пакета. Сервер сравнивает его со своими часами и
  при устойчивом расхождении переустанавливает системное время:

    • порог            : 30 с (переменная окружения TIME_SYNC_THRESHOLD)
    • подтверждение    : 3 пакета подряд с одинаковым расхождением (разброс ≤ 10 с)
    • не чаще          : одного раза в 5 минут
    • отключить        : Environment=TIME_SYNC=0 в systemd-юните

  Механизм: server/timeSync.js → sudo /usr/local/lib/drillmonitor/set-time.sh
  <epoch> (NOPASSWD в /etc/sudoers.d/drillmonitor, ставится install.sh, см.
  раздел 17). Каждая корректировка пишется в логи приложения («Время сервера
  синхронизировано с BCS_Loader…»).

  Проверка вручную:
    sudo -u drillmonitor sudo -n /usr/local/lib/drillmonitor/set-time.sh $(date +%s)


13. ПРЕОБРАЗОВАТЕЛЬ ИНТЕРФЕЙСОВ WCH CH343 (USB → UART)
────────────────────────────────────────────────────────────────────────────────
  Драйвер ставить не нужно: ядро Ubuntu 24.04 (6.8) распознаёт CH343
  (VID:PID 1a86:55d3, «USB Single Serial») штатным модулем cdc_acm и создаёт
  /dev/ttyACM<N>. Проверка:

    lsusb | grep 1a86          # QinHeng Electronics USB Single Serial
    dmesg | grep cdc_acm       # cdc_acm 2-4:1.0: ttyACM0: USB ACM device

  Настройка (стабильное имя + доступ пользователей к порту):
    sudo bash scripts/setup-serial.sh
      → /dev/ttyCH343 (symlink на ttyACM<N>), группа dialout для
        drillmonitor и bcs (список: переменная SERIAL_USERS)

  Родной драйвер WCH (CH343SER_LINUX, модуль ch343, /dev/ttyCH343USB<N>)
  нужен только для нестандартных скоростей или аппаратного RTS/CTS. Он
  компилируется из исходников (gcc, make, linux-headers) — на сервере без
  интернета заранее поставить build-essential или собрать модуль на другой
  машине с тем же ядром. Windows-пакет CH343SER_EXE для сервера не подходит.


14. ПРИЁМ ДАННЫХ ПО RS-485 (BCS_DrillerMonitorLoader → МОНИТОР)
────────────────────────────────────────────────────────────────────────────────
  Loader передаёт данные одним из двух транспортов (выбор в его настройках):
    • TCP/IP — HTTP push на /api/push/data и /api/push/state;
    • RS-485 — кадры по последовательной линии через преобразователи
      (на мониторе — CH343, /dev/ttyCH343; на компьютере — COM-порт Loader).
  Монитор принимает оба транспорта одновременно; записи из обоих идут в один
  конвейер (server/ingest.js): индикаторы, SSE, синхронизация часов.

  Кадр (server/serialFrame.js):
    STX(0x02) <JSON UTF-8> ETX(0x03) <CRC16 4 hex> CR LF
    JSON — тело как у /api/push/data: {"recNo","depth","time","params":{...}}
           или состояние: {"state":{"running":false,"reason":"..."}}
    CRC  — CRC-16/MODBUS по байтам JSON (crc("123456789") = 4B37)
    Параметры линии: 8N1, без управления потоком. Скорость по умолчанию
    57600 бод — с запасом по дальности для линии от 100 м (на коротких
    линиях можно 115200). При 9600 кадр со всеми 255 параметрами (~4 КБ)
    идёт ~4 с — для полного набора параметров нужна скорость от 57600.

  Настройка приёма:
    • из BCS_DrillerMonitorLoader — «Сеть табло»: включён/выключен, порт,
      скорость; по TCP (POST /api/serial) или кадром {"serial":…} по линии.
      Сохраняется в server/data/serial-settings.json, перезагрузка не нужна;
    • переменные окружения в юните имеют приоритет:
      SERIAL_ENABLED=0|1, SERIAL_PORT=/dev/ttyCH343, SERIAL_BAUD=57600.
    На самом табло настроек нет (см. раздел 16).
    Порт открывается без сторонних модулей: stty + чтение устройства как
    файла; если порт отсутствует, попытки повторяются каждые 10 с.

  Диагностика:
    curl http://localhost/api/serial              # состояние приёмника
    sudo stty -F /dev/ttyCH343 -a | head -1       # текущая скорость порта
    Пользователь сервиса должен состоять в группе dialout (setup-serial.sh).

    Сырой поток с линии смотреть только при ОСТАНОВЛЕННОЙ службе (иначе порт
    читают двое) и обязательно выставив min 1 time 0 — служба держит порт в
    режиме min 0 time 5, и в нём `cat` выходит сразу на первом пустом чтении,
    создавая ложное впечатление мёртвой линии:
      sudo systemctl stop drillmonitor
      sudo stty -F /dev/ttyCH343 57600 raw -echo min 1 time 0
      sudo timeout 20 cat /dev/ttyCH343 | od -c
      sudo systemctl start drillmonitor


15. САМОДИАГНОСТИКА И САМОВОССТАНОВЛЕНИЕ
────────────────────────────────────────────────────────────────────────────────
  К табло на буровой подойти трудно: ни клавиатуры, ни (часто) сети. Поэтому
  неисправность должна либо чиниться сама, либо дождаться в журнале того, кто
  однажды подключится. Раз в 5 секунд сервер опрашивает подсистемы
  (server/selfCheck.js) и пишет в журнал только ПЕРЕХОДЫ: когда стало плохо и
  когда стало хорошо — с длительностью неисправности.

  Что проверяется и что чинится само:
    • RS-485     — порт исчез или переподключился по USB: сторож
                   (server/serialSource.js) закрывает мёртвый дескриптор и
                   открывает порт заново; если ссылки /dev/ttyCH343 нет вовсе,
                   берётся единственный найденный преобразователь (WCH, FTDI,
                   SiLabs, Prolific) — и штатный узел возвращается, как только
                   появится. Молчание линии дольше 5 мин — до 3 попыток
                   переоткрыть порт, не чаще раза в 10 минут.
    • Данные     — обрыв потока от Loader (любой транспорт) с длительностью.
    • Диск       — при заполнении чистятся брошенные каталоги HLS, старые
                   резервные копии обновлений и логи старше недели.
    • Память     — предупреждение при нехватке (по /proc/meminfo).
    • Часы       — отметка, что время ещё не получено от Loader.
    • Видео      — упавший ffmpeg перезапускается сам с нарастающей паузой
                   (2 с → 30 с), браузер переподключается к потоку.
    • Служба     — «процесс жив, но не отвечает» изнутри не чинится: раз в
                   минуту снаружи (drillmonitor-watchdog.timer →
                   /usr/local/lib/drillmonitor/healthcheck.sh) опрашивается /api/health, и после
                   трёх неудач подряд служба перезапускается, но не чаще раза
                   в 10 минут. Запись об этом ложится в
                   server/data/watchdog.log и переносится в общий журнал при
                   следующем запуске.

  Где смотреть:
    curl http://localhost/api/health | python3 -m json.tool   # сводка
    веб-интерфейс → «Логи системы» — состояние подсистем и история
    sudo journalctl -u drillmonitor -b -1       # журнал прошлой загрузки
    sudo systemctl list-timers | grep drillmonitor

  Журнал systemd сохраняется на диск (Storage=persistent, до 200 МБ) — записи
  переживают перезагрузку. Сама служба перезапускается при любом завершении
  (Restart=always) и без ограничения числа попыток: лучше пробовать вечно,
  чем оставить бурильщика перед тёмным экраном.

16. ТАБЛО НИЧЕГО НЕ НАСТРАИВАЕТ И НЕ ПРЕОБРАЗУЕТ
────────────────────────────────────────────────────────────────────────────────
  Разделение ролей (решение заказчика): данные готовит BCS_DrillerMonitorLoader,
  табло их только показывает.

  Данные. Принятые значения кладутся как есть, по номерам параметров из пакета.
  Табло не пересчитывает единицы и не подменяет значения по своему справочнику
  (раньше поле depth записи затирало параметры с именами «глубина забоя» и
  «глубина долота» — это было второе преобразование тех же данных).

  Настройки. В веб-интерфейсе табло остались только рабочее поле, окно «Логи
  системы» с самодиагностикой и версия программы. Всё остальное задаётся из
  Loader — по TCP/IP или по RS-485:
    раскладка и профили  POST /api/push/config  либо кадр {"config":…}
    сеть устройства      POST /api/network       либо кадр {"net":…}
    приём по RS-485      POST /api/serial        либо кадр {"serial":…}
    пароль admin         POST /api/auth/password либо кадр {"auth":…}
    обновление программы POST /api/update/package либо кадр {"upd":…}
    журнал               GET/DELETE /api/logs
  Эти маршруты — интерфейс для Loader, а не для человека: вход по паролю на
  самом табло убран, окон настройки нет.

  Справочников на табло нет. Параметры, единицы измерения и типы данных с
  версии 1.8.0 хранит Loader (файл references.json рядом с программой): табло
  ими не пользовалось ни для показа, ни для приёма данных — номер параметра в
  пакете это просто номер слота, а заголовок и единицы лежат в самом
  индикаторе. Маршруты /api/parameters, /api/units, /api/data-types и кадр
  {"refs":…} убраны.

  На табло осталось одно действие оператора: квитировать сработавшую тревогу
  (правый щелчок по индикатору в тревоге — «Квитировать тревогу»), чтобы
  заглушить сирену. Сами тревоги решает табло — см. раздел 18.

17. ПРАВА И ДЕЙСТВИЯ ОТ ROOT
────────────────────────────────────────────────────────────────────────────────
  Служба работает от пользователя drillmonitor. Права разделены так:

    /opt/drillmonitor                 root, служба только читает
    /opt/drillmonitor/server/data     drillmonitor — база и настройки
    /opt/drillmonitor/backup          root — копии прежних версий
    /tmp/drillmonitor_hls             drillmonitor — видеопотоки
    /usr/local/lib/drillmonitor/      root — помощники, см. ниже

  Root служба получает только через помощники (sudo NOPASSWD,
  /etc/sudoers.d/drillmonitor):
    set-network.sh   dhcp | static a.b.c.d/p | reboot
    set-time.sh      <epoch>
    apply-update.py  <пакет.tgz> — установка пакета обновления (раздел 9)
  и через сторожа healthcheck.sh, которого запускает systemd. Каждый помощник
  сам проверяет свои аргументы: вызвать его может любой код службы.

  Почему так. Раньше весь каталог программы принадлежал службе, и помощники
  лежали в нём же (scripts/). Служба могла переписать скрипт, который сама
  запускает от root, а пакет обновления распаковывался прямо в scripts/ —
  любой её сбой или любой пакет давал root на устройстве. Теперь пакет
  ставит в каталог программы код, который работает с правами службы, а
  помощников не трогает.

  NoNewPrivileges в юните службы выключен: с ним sudo не запускается вовсе.

  Перевод уже установленного табло — сам, обычным обновлением из Loader:
    1. Табло старой установки распаковывает пакет по-старому и
       перезагружается.
    2. Через 30 с после запуска служба видит, что код всё ещё принадлежит
       ей (server/migrateLayout.js), и по sudo просит прежний
       scripts/set-network.sh выполнить migrate.
    3. Тот через systemd-run (вне песочницы службы) запускает
       scripts/migrate-layout.sh: проверки, помощники в
       /usr/local/lib/drillmonitor, переходный sudoers (старые и новые пути),
       код — root, server/data — службе, итоговый sudoers (только новые
       пути), из юнита убирается NoNewPrivileges, сторож — из каталога
       помощников. Затем служба перезапускается.
  Итог — запись «Внешний сторож: табло переведено на новые права…» или
  «…перевод не выполнен: <причина>» в журнале табло (Loader → «Журнал»).
  Перевод ничего не меняет, пока не пройдены проверки, а оборвавшийся
  посередине оставляет табло рабочим: служба выбирает пути по владельцу
  кода, и на время перевода sudoers разрешает оба набора.

  Сам перевод невозможен, если на табло не работает sudo — например, в юните
  уже стоит NoNewPrivileges=yes (sudo под ним не запускается) или нет
  sudoers. Тогда в журнале будет «Перевод табло на новые права не запущен»,
  табло продолжит работать по-старому, и перевести его можно только на месте
  (по SSH или с клавиатуры):
    cd /opt/drillmonitor && sudo bash install.sh
  install.sh делает то же самое и годится для любой установки.

  Проверка:
    stat -c '%U %a %n' /opt/drillmonitor /opt/drillmonitor/server/data
    sudo cat /etc/sudoers.d/drillmonitor
    sudo -u drillmonitor sudo -n -l

18. ТРЕВОГИ
────────────────────────────────────────────────────────────────────────────────
  Тревогу решает табло, а не Loader и не браузер киоска (server/alarm.js).
  Loader шлёт только значения; табло сравнивает каждое с порогами индикаторов
  активного профиля и пересчитывает состояние по каждой записи заново.
  Отдельного сообщения «тревога кончилась» нет — потерять его нельзя: потерянную
  запись лечит следующая.

  Тревога привязана к параметру и его порогам, а не к строке индикатора:
  сохранение раскладки из Loader не обрывает и не дублирует идущую тревогу.
  Прочерк (параметр пропал) состояние тревоги не меняет.

  Оповещение:
    • свет  — индикатор мигает цветом тревоги; при любой тревоге, всегда;
    • звук  — по настройке профиля «Чем звучит» (Loader → Настройки рабочего
              поля): динамик киоска (выбранный звук, повтор с заданной паузой)
              или внешний оповещатель (реле на Digispark, server/annunciator.js).
              Оповещатель не отвечает — звук сразу идёт через динамик, на
              экране и в журнале сказано почему.

  Квитирование — правый щелчок по индикатору в тревоге или долгое нажатие
  кнопки на плате: звук смолкает, свет держится, пока значение не вернётся в
  норму.

  Данных нет: тревога держится 10 с, затем звук и реле гаснут, индикатор
  остаётся в цвете тревоги (без мигания), на экране — «Нет данных — состояние
  тревоги неизвестно». Придут данные — состояние пересчитается.

  История — таблица alarms в базе: одна строка на тревогу (начало, худшее
  значение, квитирование, конец и его причина), хранятся последние 5000.
  Переживает перезагрузку; незакрытые при перезапуске строки закрываются с
  причиной «перезапуск табла». Loader читает её вкладкой «Тревоги» (обмен
  alarm.history) по кнопке; в общий журнал по-прежнему пишутся строки
  «[Сигнализация] ТРЕВОГА/СБРОС/КВИТИРОВАНИЕ».

  Маршруты киоска: GET /api/alarms/state, POST /api/alarms/ack {key},
  событие SSE «alarm-state».

19. ОПОВЕЩАТЕЛЬ И КНОПКА (DIGISPARK)
────────────────────────────────────────────────────────────────────────────────
  Плата Digispark (ATtiny85, Model A) в любом USB-разъёме табла:
    P0 — реле оповещателя (модуль с оптопарой, активный высокий уровень)
    P1 — штатный светодиод: вспышка раз в секунду — связь с табло есть;
         горит 0,2 с — табло приняло нажатие; погашен — связи нет
    P2 — кнопка на GND, подтяжка 10 кОм на 5 В
  Кнопка: короткое нажатие — следующий профиль по кругу; от 2 с — квитировать
  все тревоги. Решает табло (server/annunciator.js), плата только сообщает.

  Связь — HID (16c0:05df, «drillmonitor.bcs Annunciator»), сервер читает
  /dev/hidraw* как файл. Доступ даёт правило
  /etc/udev/rules.d/99-drillmonitor-annunciator.rules (install.sh или
  автоматический перевод прав, раздел 17). Сторож в прошивке: нет команды от
  табла 3 с — реле размыкается. Самодиагностика: проверка «Оповещатель».

  Прошивка — firmware/annunciator/annunciator.ino. Сборка на ПК с Arduino IDE 2
  и ядром Digistump AVR 1.6.7:
    powershell -ExecutionPolicy Bypass -File firmware\annunciator\build.ps1
  Драйвер V-USB берётся из установленной библиотеки DigisparkKeyboard, в
  репозитории его нет. Заливать с табла (на ПК с USB 3 загрузчик не
  отвечает): скопировать annunciator.hex на табло, затем
    sudo ~/tools/micronucleus --run annunciator.hex
  и вставить плату в USB — загрузчик слушает первые ~5 с после подачи питания.
  Проверка: lsusb | grep 16c0:05df; ls -l /dev/hidraw*.
